# ButtonSpa Export Pipeline — Deep Dive

How a designed button actually leaves the studio: HTML export, share link, and
"save to phone" PWA. Traced end to end against the code as of 2026-07-18, not
the aspirational plan in `docs/PWA_FLOW.md` (that file is an earlier design doc
— useful for history, not for what's actually running).

## The one-sentence version

**There is no separate "share link" system and "PWA" system.** Both "Copy link"
and "Save to phone" produce the exact same URL shape —
`/b/{base64-encoded-button-config}` — served by `routes/b/[id].tsx`. The only
difference is which UI you clicked to get it. "HTML export" is the one genuinely
different path: a real file download, self-contained except for one network
call.

---

## 1. The three outputs, traced

### 1a. HTML/CSS export

**Entry point:** `components/panels/ShipPanel.tsx` → "Export code" button →
`handleExport("html")` → `ButtonExporter.generateHTML()`
(`utils/export/ButtonExporter.ts:52`) → `generateStandaloneHTML()`
(`utils/export/templates/html-standalone.ts`, ~1983 lines, the single largest
file in the export system).

**What's actually in the file:**

- A full `<!DOCTYPE html>` document, single file, no build step to run it.
- **Inline `<style>` block** built from two sources:
  - `getCustomCSS()` (line 1645) — generates the effect `@keyframes` fresh, from
    `customization.effects` (breathing/bounce/glow/pulse/shine). This is a
    **separate CSS generator from the in-app one** in
    `components/VoiceButton.tsx` — same effect names, independently hand-written
    keyframes in each. They currently produce visually similar but not
    byte-identical animations (e.g. breathe scales to 1.05 in both, but
    bounce/glow durations and easing were typed out twice, so future edits to
    one won't automatically apply to the other — see Gaps).
  - A large block of hand-written layout/card/button CSS for the standalone page
    shell (spacing scale, card shadow, install banner, output card, recording
    meter, history list) — this is bespoke to the export, not shared with the
    in-app editor's Tailwind classes at all.
- **Inline `<script>`** — the full voice-recording state machine: `getUserMedia`
  → `MediaRecorder` → base64-encode the blob → `fetch()` to
  `https://buttonspa.app/api/transcribe` (hardcoded URL,
  `html-standalone.ts:764`) → render result as plain text / checklist / sections
  depending on `customization.api.format` → clipboard copy → append to a
  `localStorage` history list keyed by a hash of the button's label
  (`buttonspa-history-{hash}`, so re-exports of "the same" button share history,
  but a renamed button starts fresh).
- **No API key of any kind is embedded.** The exported page never asks for one
  and never stores one. See §1c for why.

**What works standalone vs needs the app:**

- Works standalone: opening the HTML file directly (`file://` or any static
  host) renders the full button, all effects, all interaction juice
  (hover/press/squish), voice recording UI, history.
- Needs the network (not "the app," but _a_ network): every transcription
  request round-trips to `buttonspa.app/api/transcribe`. No local host, no
  offline model, no user-supplied key path exists. If `buttonspa.app` is down,
  the button still opens and records audio, but transcription always fails —
  there is no fallback.
- The "install as PWA" banner code is present in this same template
  (`showInstallGuide` option, `getInstallGuideMarkup()` /
  `getInstallGuideScript()`) but only turned on when `ButtonExporter` calls
  `generatePWAHTML()` — the plain "Export code" HTML from ShipPanel does **not**
  pass `showInstallGuide: true`, so a manually-downloaded HTML file has no
  manifest link, no install banner, no service-worker registration. It's a plain
  page, not a PWA, even though it's generated by the same function family.

### 1b. Share link

**Entry point:** `components/panels/ShipPanel.tsx` → "Copy link" →
`encodeHostedButtonConfig(customization)` (`utils/export/hostedConfigCodec.ts`)
→ clipboard gets `{origin}/b/{id}`.

**Encoding:** the _entire_ `ButtonCustomization` object (appearance,
interactions, content, effects, sound, recording, custom prompt/format) is
`JSON.stringify`'d, UTF-8-encoded, base64'd, then made URL-safe (`+`→`-`,
`/`→`_`, strip `=` padding). No compression (there's a
`compressString()`/`decompressString()` pair in `utils/export/shareLink.ts`
that's a literal no-op pass-through — see Gaps).

**There is no server storage.** The "id" in `/b/{id}` _is_ the button, not a
lookup key. `routes/b/[id].tsx` decodes it on every request via
`createHostedButtonExporter()` (`utils/export/hostedPwa.ts`), which calls
`decodeHostedButtonConfig()` → `normalizeHostedCustomization()` →
`sanitizeHostedCustomization()`. That sanitize step is a real, careful allowlist
pass — every enum field is checked against its known values, colors are
regex-validated as `#rrggbb`, numbers are clamped to their real ranges, text
fields are stripped of control characters and `<`/`>` and capped in length. This
matters because the "id" is fully attacker-controlled input (anyone can
hand-craft a base64 blob); the sanitizer is what stops a malicious share link
from injecting HTML/JS into the rendered page.

**What survives:** since forever — there's no expiry, no database row to go
stale, no server dependency for the _data_. The link only breaks if
`buttonspa.app` itself goes down, or if a future app version changes the
`ButtonCustomization` shape in a way `normalizeHostedCustomization()` can't
gracefully default around (there's a `version` field in
`utils/export/types.ts`'s `ShareLinkData`, but note: that versioned
`generateShareLink()`/`parseShareLink()` pair in `shareLink.ts` is **dead code**
— see Gaps — the live path uses the unversioned `hostedConfigCodec.ts` instead,
which has no version field at all).

**What the recipient sees:** exactly the PWA-flavored HTML from §1c below — full
button, install banner, voice recording wired to the same
`buttonspa.app/api/transcribe` endpoint. There is no separate "view-only
preview" — a share link and an install link are the same artifact.

**Old share code that looks live but isn't:** `utils/export/shareLink.ts`'s
`generateShareLink()` / `parseShareLink()` / `checkForShareLink()` /
`generatePreviewUrl()` (uses a `bs://` prefix, a different encoding scheme) are
never imported by any route or island — confirmed via repo-wide grep.
`ButtonExporter.generateShareLink()` calls into this file too, but
`ButtonExporter` itself isn't used for share/PWA generation in the live UI
(`ShipPanel`/`PWAShareModal` both call `hostedConfigCodec.ts` directly). This
whole `bs://`-prefixed system is orphaned.

### 1c. PWA export ("save a button to your phone")

**Entry point:** `components/PWAShareModal.tsx` (opened from ShipPanel's "Save
to phone" button) → same `encodeHostedButtonConfig()` as the share link →
`{origin}/b/{id}` → QR code rendered via a **third-party API call** to
`api.qrserver.com` (not self-hosted, not QRBuddy despite the old `PWA_FLOW.md`
plan to integrate it).

**Server side, three routes, all keyed off the same encoded `id` query param or
path segment:**

- `routes/b/[id].tsx` — serves the actual page HTML. Calls
  `exporter.generatePWAHTML()`, which injects PWA `<head>` tags (manifest link,
  theme-color, apple-touch-icon links) and a service-worker registration script
  into the same `generateStandaloneHTML()` output from §1a, with
  `showInstallGuide: true` this time.
- `routes/b/manifest.json.ts` — serves a per-button `manifest.json` generated by
  `ButtonExporter.generatePWAManifest()`, `theme_color` pulled from the button's
  own fill color, icons pointed at the routes below.
- `routes/b/icon-192.png.ts`, `icon-512.png.ts`, `apple-touch-icon.png.ts` —
  each calls `serveHostedIconAsset()` → `iconRenderer.ts`, which **renders the
  actual button design** as SVG (real gradient/solid fill, border, shadow, glow
  filter, the button's own emoji/text content via Noto Emoji SVGs or a
  fitted-text `<text>` node) and rasterizes it to PNG server-side using
  `@resvg/resvg-wasm` + a bundled Inter font
  (`static/vendor/resvg/index_bg.wasm`, `static/vendor/fonts/inter.ttf`). This
  is a genuinely nice detail — the home-screen icon is not a generic ButtonSpa
  logo, it's your actual button, rendered pixel-accurate.

**Service worker — the important nuance:** there are **two separate service
worker files** in this codebase and they serve different scopes:

- `static/sw.js` — the main ButtonSpa **app's** own service worker (registered
  by `static/register-sw.js`, cache name `buttonspa-v2`), caches the studio app
  shell itself. Not related to exported buttons.
- `ButtonExporter.generateServiceWorker()` — generates a _second_,
  differently-named service worker (`voice-button-v1` cache) meant for the
  ZIP-based PWA export path. **This function is never actually served by any
  route** for the hosted `/b/[id]` flow — `getHostedPwaAssetPaths()`
  (`hostedPwa.ts:51`) sets `serviceWorker: "/sw.js"`, i.e. every installed
  button's manifest and registration script point at the **main app's**
  `static/sw.js`, not a button-specific one. That file's own cache list
  (`urlsToCache`) is hardcoded to ButtonSpa's own root-level assets (`/`,
  `/styles.css`, `/manifest.json`, root icons) — it does **not** include the
  button's own `/b/{id}` page or per-button icon URLs.

  The registration script (`generatePWAHTML`, `html-standalone.ts:448-467`) does
  try to compensate: after registering, it posts a `CACHE_URLS` message to the
  worker with `[window.location.href, ...pwaAssetUrls]` (the button's own page +
  its manifest/icons), and `static/sw.js` does handle that message type by
  caching those URLs into its own `buttonspa-v2` cache. So **in practice this
  does work** — the button's own page and icons do get cached — but it's a
  fragile two-hop path (one shared SW, dynamically told at runtime to cache each
  installed button's assets into a cache keyed by the main app's cache name)
  rather than a clean per-button PWA. If a user clears the main app's cache, or
  if `buttonspa.app`'s root SW registration ever changes its cache name/scope,
  every installed button's offline cache silently resets too.

**What ACTUALLY happens on the phone, concretely:**

- **Install flow:** works as a real PWA. `beforeinstallprompt` is captured and
  surfaced through a custom install banner (`getInstallGuideScript()`) on
  Android/Chrome; iOS gets a "Share → Add to Home Screen" instruction banner
  since Safari doesn't support the native prompt. Icon on the home screen is the
  real rendered button (§ above).
- **Offline: the page shell loads offline** once visited once (cached via the
  CACHE_URLS handshake above). The button renders, effects animate, the record
  button works (mic access + `MediaRecorder` are local device APIs, no network
  needed to _capture_ audio).
- **Offline: transcription does NOT work offline.** There is no local model, no
  queued/background-sync retry despite `static/sw.js` having a `sync` event
  listener stub (`syncTranscriptions()` — logs a message and resolves
  immediately, does nothing; dead placeholder, see Gaps). Recording while
  offline will complete, then the `fetch()` to `buttonspa.app/api/transcribe`
  will fail, and the button surfaces whatever its (now warmed, previously red)
  error state shows.
- **Mic permissions:** standard browser/OS permission prompt on first record
  tap, same as any web page — no special PWA wrinkle.
- **API key handling — where does it live, and is it safe:** it doesn't live
  anywhere client-side, in any of the three export paths. ButtonSpa's own server
  (`routes/api/transcribe.ts`) holds `OPENROUTER_API_KEY` as a Deno env var and
  proxies every transcription request to OpenRouter (model list spans
  `google/gemini-2.5-flash-lite`, `mistralai/voxtral-small-24b-2507`, and
  premium-tier Gemini/Mistral variants — **not a direct Gemini API
  integration**, despite the README and UI copy saying "Gemini" prior to this
  pass). This is the _safe_ design: no key of any kind ships in an exported
  file, a shared link, or an installed PWA. The tradeoff is the one already
  stated above — every installed button is permanently a client of
  `buttonspa.app`'s server, forever, with no offline or self-hosted fallback,
  and is subject to ButtonSpa's own rate limits (20/day free, 500/day premium
  via `premiumToken`, IP-keyed).

## 2. Effects → visual map

The UI-exposed effects are **breathing, bounce, glow, shadow, shine, pulse** —
six toggles across `FeelPanel.tsx`'s "Movement" (breathing, bounce) and "Visual"
(glow, shadow, shine) groups, plus `pulse` which has no manual toggle in the UI
but is used by the recording state and the shuffle/"surprise me" randomizer
(`islands/ButtonStudio.tsx:379`).

**Wiggle and rainbow are not live effects.** They exist in the type
(`EffectToggles.wiggle?`, `.rainbow?`, `.rainbowGlow?`,
`types/customization.ts:140-143`, explicitly commented "Legacy effects (kept for
compatibility but not shown in UI)") and have working CSS in
`components/VoiceButton.tsx` (`@keyframes wiggle` line 809, `rainbow-rotate`
line 888), but nothing in the current editor UI can turn them on, and the export
template (`html-standalone.ts`) has **no wiggle/rainbow CSS at all** —
`getCustomCSS()` only handles breathing/bounce/glow/pulse/shine. So even a
hand-crafted share-link payload with `wiggle: true` would animate in the in-app
preview (if you could set it) but render static in every export. README
previously listed Wiggle and Rainbow as current features — fixed in this pass
(see below).

| Effect                | Technique                                                                    | GPU-accelerated?                    | In-app (VoiceButton.tsx)                                   | HTML export                                | Share link (`/b/[id]`)    | PWA (`/b/[id]`) |
| --------------------- | ---------------------------------------------------------------------------- | ----------------------------------- | ---------------------------------------------------------- | ------------------------------------------ | ------------------------- | --------------- |
| Breathe               | CSS `@keyframes` on `transform: scale()`                                     | Yes (compositor-only)               | ✅ works                                                   | ✅ works (own keyframes in `getCustomCSS`) | ✅ works (same generator) | ✅ works        |
| Bounce                | CSS `@keyframes` on `transform: translateY()`                                | Yes                                 | ✅ works                                                   | ✅ works                                   | ✅ works                  | ✅ works        |
| Glow                  | CSS `@keyframes` on `box-shadow`                                             | No (paint, not compositor)          | ✅ works (inline style, not a class)                       | ✅ works                                   | ✅ works                  | ✅ works        |
| Shadow                | Static `box-shadow` (not animated)                                           | N/A (static)                        | ✅ works                                                   | ✅ works                                   | ✅ works                  | ✅ works        |
| Shine                 | CSS `@keyframes` on `::after` pseudo-element `left` position                 | No (`left` triggers layout)         | ✅ works                                                   | ✅ works                                   | ✅ works                  | ✅ works        |
| Pulse                 | CSS `@keyframes` on `opacity` (+ `filter: brightness` in-app only)           | Mostly (`opacity` yes, `filter` no) | ✅ works (not UI-toggleable, used by randomizer/recording) | ✅ works                                   | ✅ works                  | ✅ works        |
| Wiggle                | CSS `@keyframes` on `transform: rotate()`                                    | Yes                                 | ⚠️ code exists, unreachable from UI                        | ❌ not implemented in export CSS           | ❌ same as HTML export    | ❌ same         |
| Rainbow / rainbowGlow | CSS `@keyframes` on `background-position` (animated gradient border wrapper) | No (`background-position` repaints) | ⚠️ code exists, unreachable from UI                        | ❌ not implemented                         | ❌ same                   | ❌ same         |

All six live effects use plain declarative CSS `@keyframes` — no Web Animations
API, no rAF-driven JS anywhere in the effect system (rAF _is_ used elsewhere,
for the live audio level meter during recording, which is a genuinely different,
necessarily-JS-driven feature). `shadow` isn't animated at all — it's a static
box-shadow toggle, not really a "movement/visual effect" in the same sense as
the other five, more of an on/off style flag.

**Duplication risk:** the in-app effect CSS (`VoiceButton.tsx`, inline
`<style jsx>` block starting ~line 764) and the export CSS
(`html-standalone.ts`'s `getCustomCSS()`, line 1645) are two independent,
hand-written copies of the same five keyframe sets. They already agree closely
(breathe scales to 1.05 in both) but nothing enforces they stay in sync — a
future tweak to one (e.g. "make bounce snappier") has to be manually mirrored
into the other or the in-app preview will lie about what gets exported.

## 3. The gaps, ranked

Ranked by what most threatens the "shared, embedded, installed, and wired"
promise in the README — i.e., what would make a real user's exported/shared
button feel broken or untrustworthy.

1. **Every export outlives `buttonspa.app`'s uptime, and users aren't told
   that.** This is the biggest gap in the "trust the pipeline" sense Pablo asked
   about. Nothing in the export flow, the ShipPanel copy, or the install banner
   says "this button will stop transcribing forever if buttonspa.app goes down."
   The ShipPanel's own claim ("No API key needed — exports call ButtonSpa, not
   you", fixed this pass from a stale Gemini mention) is accurate but doesn't
   disclose the flip side of that tradeoff. Fix priority: either add a one-line
   disclosure in the export/share UI, or — bigger lift — let power users plug in
   their own OpenRouter/Gemini key for a self-hosted transcribe endpoint (the
   React Native/Capacitor instructions already gesture at "swap in your own
   backend," so the escape hatch is half-designed already).

2. **The service worker for installed buttons is one shared, dynamically patched
   cache, not a real per-button PWA.** Detailed in §1c. It works today via the
   `CACHE_URLS` postMessage handshake, but it's fragile: one `static/sw.js` for
   the entire app and every installed button, no per-button cache isolation, a
   dead `sync` event stub that implies background retry exists when it doesn't.
   If Pablo wants "installed button truly works offline" to be a real promise
   rather than an accidental side effect of a shared cache, this needs its own
   dedicated worker per hosted button (scoped to `/b/`, which
   `getHostedPwaAssetPaths()` already sets as the manifest `scope` — the
   plumbing is half there).

3. **Two dead/orphaned subsystems create confusion for future-Pablo (or
   future-agent) debugging this code.** `utils/export/shareLink.ts`'s entire
   `bs://`-prefixed encode/decode/version system is unreachable — the live
   share/PWA path uses `hostedConfigCodec.ts` instead, which has no version
   field, no compression (the `compressString`/`decompressString` pair in
   `shareLink.ts` are literal no-ops — dead weight even inside dead code).
   Similarly, `ButtonExporter.generatePWA()` / `generateServiceWorker()` /
   `getPWAInstructions()` (the ZIP-package path) and `generateMobileTemplate()`
   (React Native/Capacitor scaffolds) are fully-built but have **zero UI entry
   points** — the ZIP button is explicitly commented out in `ShipPanel.tsx`
   ("not useful for most users"), and no panel calls `generateMobileTemplate` at
   all. None of this is broken, exactly, but ~40% of `ButtonExporter.ts` is
   unreachable from the app. Worth a deletion pass so the file matches what's
   actually shippable.

4. **Wiggle/rainbow are half a ghost feature.** Type-level support, working
   in-app CSS, zero UI access, zero export support. Either finish them (add to
   `FeelPanel`, port the keyframes into `getCustomCSS()`) or delete them
   outright — the current "commented out but half-alive" state is the worst of
   both, and it's what caused the README to overclaim (now fixed).

5. **Effect CSS is duplicated by hand between the in-app preview and the export
   template**, as noted in §2. Low urgency today (they agree), but it's a
   silent-drift risk — worth extracting `getCustomCSS()`'s five keyframe blocks
   into one shared source both `VoiceButton.tsx` and `html-standalone.ts`
   import, so "what you see in the studio" and "what ships" are structurally
   guaranteed to match, not just currently matching by discipline.

6. **QR codes leak the button's destination URL to a third party.**
   `PWAShareModal.tsx` calls `api.qrserver.com` directly with the plaintext
   share URL as a query param. Low severity (the URL itself isn't secret — it's
   the same thing being shared anyway), but it is an unnecessary external
   dependency for something a `qrcode` npm package could render fully
   client-side, and it's a small privacy leak of "someone is generating a QR for
   this specific button right now" to a third party.

## 4. Cross-fleet note: ButtonSpa wiggle vs softstack-charms wiggle

ButtonSpa's `wiggle` (`components/VoiceButton.tsx`, `@keyframes wiggle`,
`rotate(-2deg)`/`rotate(2deg)` alternation) and the wiggle being built tonight
in `~/Projects/active/apps/softstack-charms/src/wiggle/` are solving genuinely
different problems and probably shouldn't converge as-is. ButtonSpa's version is
a continuous idle-state _button effect_ — one of several always-on decorative
animations a user explicitly opts a button into, alongside breathe/bounce/glow,
meant to run forever while the button sits idle. softstack-charms'
`wiggle.js`/`wiggle.css` is a much more deliberate _attention charm_: periodic
(not continuous), show-once via localStorage per-id memory, respects
`prefers-reduced-motion` with a static ring fallback, carries an optional
tooltip, and is explicitly built as a cross-app "push me" nudge for any DOM
element in the fleet, not button-specific. Given ButtonSpa's own wiggle is
currently unreachable dead code (see Gap #4), there's a real opportunity —
if/when Pablo decides to revive it — to just adopt the softstack-charms version
wholesale instead of writing a third implementation: swap ButtonSpa's
`@keyframes wiggle` for an import of the shared charm, expose it in `FeelPanel`
as "Wiggle," and get reduced-motion support and show-once-per-visitor behavior
for free rather than reinventing it. Until that revival happens, no action
needed — they're independent and not currently in conflict.
